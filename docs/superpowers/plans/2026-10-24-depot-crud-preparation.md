Names/placeholders only; all configuration is server-only and parsed lazily on auth/protected requests:

| --- | --- |

| AUTH_SESSION_SECRET | Independent high-entropy secret (at least 32 random bytes encoded as text; library minimum 32 characters). Never the admin password or database credential. |

| UPSTASH_REDIS_REST_URL / UPSTASH_REDIS_REST_TOKEN | Private, approved limiter endpoint/credential for this environment. Never DATABASE_URL or TiDB credentials. |

No real values, PHC hash, example password or default secret is committed. Keep Dev/Testing/Production usernames/passwords, session secrets and limiter credentials separate; different cookie names and limiter namespaces per APP_ENV. Never inherit Production configuration into Preview. Hosted Preview uses one exact approved origin, not *.vercel.app; QA waits for a matching deployment/origin. Lazy imports/build/offline tests require no private configuration or network.

[PLANNED] @node-rs/argon2 owns hashing/salt generation and verification. Explicit Argon2id v19 policy: memoryCost=19456 KiB, timeCost=2, parallelism=1, hashLength=32, library-generated salt >=16 bytes; reject malformed/oversized PHC or different/unbounded work factors before KDF execution. These are OWASP-minimum starting parameters, not measured Vercel performance. [VERIFY] Node 24 Windows/Linux binary/build compatibility and bounded execution cost before release. Real password/hash creation is future private human handoff, not this task or an automatic setup script.

Login input: strict {username,password}; username matches the configured rules; password 15..128 Unicode code points, max 512 UTF-8 bytes, no trimming/normalization/truncation. Owner chooses a unique strong password per environment. Apply a 4 KiB streamed JSON cap before parsing. Wrong username and wrong password return the same generic 401; verify the configured hash for either syntactically valid username, then combine both results, avoiding a username-only timing shortcut. Invalid config/hash/limiter configuration -> generic 503, zero password verification/DB acquisition; no fallback account.

### 3.4 Login, session, logout and server authorization

- [PLANNED] GET /login is a small TailAdmin-styled username/password form. POST /api/auth/login is the only login action; no catch-all auth route or registration/reset endpoint. Order: lazy valid config/context -> strict Origin/media/body checks -> shared attempt limit -> credential verification -> fresh library session save. Return 200 {ok:true} only after save completes; invalid credentials 401, denied attempt 429 with bounded Retry-After, limiter/config failure 503. No login redirect query; client navigates only to fixed /depots.
- iron-session getIronSession(await cookies(), options) supplies sealing/unsealing; no custom JWT, signer, key protocol or seal implementation. A new successful login replaces, rather than merges, any incoming session fields. Store only subject=single-admin, environment, credentialVersion, issuedAt and expiresAt. Never password/hash/DB identity. issuedAt/expiresAt are safe-integer Unix milliseconds: capture issuedAt once from the server clock after credentials are accepted for the successful login, immediately before saving its fresh session; set expiresAt=issuedAt+43_200_000. Zod validates the decrypted shape on every protected request: expected subject, current environment/version, valid integer times, no future issuedAt, expiresAt>issuedAt, expiresAt>now and lifetime <=43200 seconds (expiresAt-issuedAt <=43_200_000 milliseconds). Reject invalid, expired, tampered or mismatched sessions; no authorization from unvalidated fields.
- Session policy: absolute 12-hour / 43,200-second lifetime from successful login. Set iron-session ttl=43200 and cookie maxAge=43200. No rolling/sliding renewal, automatic extension through activity, or remember-me. The server rejects at now>=expiresAt, including exactly 43200 elapsed seconds; the explicit expiresAt check enforces this deadline even if library clock tolerance exists. Ordinary GET, protected page/API reads and other authenticated activity never change issuedAt/expiresAt or save/refresh the session. Manual logout and server-side authorization remain mandatory.
- Hosted cookie: __Host-crp-admin-<APP_ENV>, HttpOnly, Secure, SameSite=Strict, Path=/, no Domain. Local Development HTTP alone uses a distinct unprefixed cookie with Secure=false; never relax hosted flags because NODE_ENV/dev mode is set. Private/no-store auth and Depot responses; no shared cache of authenticated page/session data.
- requireAdmin() validates server session plus current config/context before any Depot repository construction/getDatabase call. Missing/expired/tampered/empty session -> API 401; authenticated but wrong subject/environment/version -> 403. Configuration unavailable -> 503. The protected dynamic /depots page redirects unauthenticated GET to fixed /login and shows safe denied/unavailable states otherwise. Client visibility, hidden controls and a client-supplied role are never authority.
- POST /api/auth/logout uses the same Origin/JSON boundary and session.destroy() before sending 200 {ok:true}; it clears even an absent/invalid browser session, does not save again, needs no limiter/TiDB, then client replaces location with fixed /login. GET cannot login/logout/mutate. Read-only Server Components never try to clear cookies.
- Explicit stateless limit: browser logout removes its cookie, but a stolen/copied stateless cookie might remain usable for up to 12 hours from successful login, even after browser logout; theft/logout does not restart that window. No claim of per-session/global immediate revocation. Future authorized credential-version/secret changes revoke sessions only where new config is running, not an old retained deployment. No session database or Redis session registry added. The owner approved the longer session policy; its increased replay-exposure window remains a documented release risk, not evidence of runtime verification. Cookies must never be captured as evidence.

### 3.5 CSRF, Origin and serverless rate limiting

All login/logout/Depot mutations accept only same-origin JSON POST/PUT/DELETE: compare exactly one valid Origin with AUTH_ORIGIN, reject missing/null/malformed/duplicate/cross-origin values with 403, require application/json, no permissive CORS or form/multipart fallback. If Sec-Fetch-Site is present, reject cross-site; this is additional defense, not authority. Exact Origin + non-simple JSON + SameSite=Strict is the CSRF design; no custom CSRF token crypto. Protect login/logout as well as Depot writes; fixed redirect destinations avoid open redirects. Root, health and readiness keep their public contracts.

[PLANNED, SERVICE APPROVAL REQUIRED] One regional Upstash Redis endpoint and @upstash/ratelimit fixedWindow(5, "15 m") for every syntactically valid login attempt, successful or failed. One constant account bucket per project/environment (not submitted username/IP/session/instance/deployment SHA), shared across all instances/deployments of that environment. Use an environment-specific prefix and a constant identifier; ignore client-forwarded IP for this minimal design. No counter reset on success. Atomic library/store operations, not an in-memory Map, enforce the bound. Fixed windows permit a boundary burst of up to 10 attempts across two adjacent windows; do not claim a strict rolling-window maximum.

Configure analytics off, no per-user credential data, one authoritative region, and no allow-through cache. Limiter timeout=1000ms; a result with reason=timeout is failure even if SDK success=true (documented SDK fail-open default). Exceptions, malformed result, timeouts and quota/service failures -> safe 503 before KDF/session save. Only an actual validated allowance proceeds; limit exhaustion ->429. No fail-open/in-memory/Development bypass; unit tests inject a fake only through test seams. [VERIFY] SDK result/timeout and retry configuration at pinned versions; bounded service errors cannot become a login success.

Trade-off: the global bucket prevents distributed username/IP evasion without collecting IPs, but attackers can deny new admin logins and generate Redis traffic. Existing valid sessions and logout do not depend on Redis; no persistent account lock or reset feature. Service latency, quota/cost caps, outage handling and cross-instance limit tests need separate owner approval/verification before any public login. Vercel Deployment Protection is useful defense-in-depth, not the shared limit or application auth. If the owner declines this service, STOP for an alternate reviewed design; never silently ship a memory-only limiter.

## 4. Data and API contract proposed for approval

Shared camelCase application DTO:
id:string, name:string, address:string|null, latitude:number, longitude:number, isActive:boolean, createdAt/updatedAt:UTC ISO strings. Database keeps snake_case columns.

Create/full-edit input: name trimmed 1..255 JS string units; address null or trimmed string max 2000 (blank -> null); finite coordinates in the exact bounds; isActive boolean (default true only on create). Reject unknown fields, client id/timestamps, empty coordinates and implicit boolean/string coercion. Address limit is a proposed engineering bound, not a new research invariant.

Canonical id/cursor parser returns bigint for repository comparisons and decimal string for the public DTO. JSON never contains a native bigint.

| Method/path | Success | Behavior |
| --- | --- | --- |
| GET /api/depots?after=ID&limit=N | 200 {data: DepotDTO[], nextCursor: string or null} | Stable id ascending; default 50, max 100; fetch limit+1; no fake total/count. Cursor and limit strictly validated. |
| POST /api/depots | 201 {data: DepotDTO} | Create with server UTC timestamps, validate returned exact insert ID and read that row. |
| GET /api/depots/[id] | 200 {data: DepotDTO} | Missing -> 404. |
| PUT /api/depots/[id] | 200 {data: DepotDTO} | Full edit of five fields; createdAt unchanged, updatedAt server UTC. Existing unchanged row is success, not a false 404. |
| DELETE /api/depots/[id] | 204 empty body | Single record only, UI confirmation; missing -> 404; recognized FK conflict -> 409. |

Common safe error: {error:{code,message,fieldErrors?}}. Invalid JSON/id/cursor/input -> 400; unsupported body media type -> 415; streamed JSON body over 16 KiB -> 413; forbidden origin -> 403; unavailable/config/provider/malformed result -> redacted 503. All Depot responses use private, no-store. Do not include SQL, params, driver statement/cause, URL, principal or stack in responses/logs.

Order: server session/current credential-version authorization -> origin for mutations -> bounded JSON/query/id validation -> environment target check -> service -> repository. All rejected preconditions have zero DB acquisition/SQL.

Environment check reuses parseDatabaseConfig, without migration credentials: local application uses development/dev database only; Vercel preview requires APP_ENV=testing/testing database; Vercel production requires APP_ENV=production/production database. Invalid/unknown/mismatched configuration fails before getDatabase. This logical-name/context guard is additional write safety, not a claim of direct physical runtime SQL identity.

## 5. Service/repository details and delete safety

- Shared pure schemas/DTO types in lib/validation/depot.ts; service owns UTC timestamp and domain/error rules; repository alone imports Drizzle and depots; getDatabase acquired lazily. Authorization remains on every exposed entry before constructing/acquiring the repository.
- Repository interface: list({after?:bigint,limit:number}) -> rows, findById(id:bigint) -> row|null, insert(inputWithDates) -> validated bigint id before service readback, update(id,inputWithUpdatedAt) -> validated affected-row count, remove(id) -> validated affected-row count. Service exports listDepots(query), getDepot(id), createDepot(input), updateDepot(id,input), deleteDepot(id), with typed DTO results. requireAdmin(), assertDepotEnvironment() and the input parsers are explicit Route Handler preconditions; dependencies are injected only in tests, never through a production bypass.
- Driver inspection at the pinned installed versions shows FullResult.lastInsertId is string|null and uses wire sLastInsertID. Drizzle tidb-serverless $returningId() uses arithmetic/increment on this metadata. Avoid $returningId() entirely.
- Use normal insert result; validate lastInsertId as the canonical positive decimal string, convert directly with BigInt, then SELECT by that ID using Drizzle. Never infer an ID from MAX(id), rowsAffected, a separate session's LAST_INSERT_ID(), or Number. Synthetic transport tests pin this path above 2^53.
- Validate mutation rowsAffected metadata; an unchanged update may report zero, so verify existence/readback before deciding 404. Handle concurrent delete without a spurious success.
- There are no actual child relations today. A physical DELETE is limited to the selected id; do NOT query non-existent scenarios, add a fake always-false reference checker, create a Scenario table, or claim live FK behavior has already been tested.
- For an existing/future enforced FK, never cascade: map only the structured recognized FK code to 409 DEPOT_IN_USE. Drizzle error.cause may contain driver details.code; do not parse or expose the message. Unknown provider error stays safe 503.
- When Scenario is introduced, its depot FK must enforce RESTRICT/no cascade, and the real referenced-depot integration test belongs to that schema change. A race-prone precheck without a FK is not sufficient.
- Inactive is NOT deleted and is NOT globally unique. Existing inactive rows remain visible with status.
- No automatic retry of create/update/delete. Any failure after SQL dispatch where commit cannot be ruled out (fetch/body/decoding, lost/invalid insert metadata, or successful insert followed by failed readback) is outcome-unknown, not proof of rollback. Return safe 503 MUTATION_OUTCOME_UNKNOWN and offer list refresh before another explicit attempt; retain no raw cause/statement. Definite validation/auth/target rejections occur before SQL; a recognized FK rejection remains 409. Do not promise global single-use/idempotency.
